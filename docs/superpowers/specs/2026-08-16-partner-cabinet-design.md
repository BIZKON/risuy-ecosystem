## 1. Задача одной фразой

Партнёр должен сам видеть, кого он привёл, сколько ему начислено и что уже
выплачено, а начисление должно происходить в момент прихода денег — без нас.

## 2. Решения владельца 16.08

| Вопрос | Решение |
|---|---|
| С каких денег процент | Со всего, что заплатил приведённый клиент |
| Что считается платежом | **Первый крупный: вход или абонплата.** Пополнения баланса токенов не считаются вовсе |
| Сколько раз | **Только первый платёж** клиента, не с каждого периода |
| Ставка продавцу | **20%** — как в ProAgent AI, чтобы партнёр не держал в голове две схемы |
| Наставничество | **Схема А:** продавцу 20%, наставнику **+5% сверх** из нашей маржи, глубина ровно 1, срок 12 месяцев от регистрации подопечного |
| Чья программа | **Наша и тенантов.** Каждый тенант сможет вести своих партнёров |
| Вход партнёра | Панель, отдельный принципал. Доступ — **одноразовая ссылка-приглашение**, пароль партнёр ставит сам |
| Выплаты | Вручную, в рублях, в системе — отметка |

## 3. Что уже построено и НЕ переносится из x10

Прямой перенос пяти таблиц был бы ошибкой. В ProAgent AI `partner_deals` и
`deal_payments` существуют потому, что сделка там — офлайн-договор на 180–350 тысяч,
который заводит человек, и платежи по нему тоже заводит человек. Здесь и атрибуция,
и платежи **уже лежат в базе**, причём в идемпотентных функциях.

| Что нужно | В x10 строили | В risuy уже есть |
|---|---|---|
| Кто кого привёл | `partner_deals` | `tenants.partner_id` ✅ · для контура тенанта добавляем `leads.partner_id` |
| Что клиент заплатил | `deal_payments` | `service_invoices` и `orders` ✅ — обе с `tenant_id`, обе с идемпотентным ядром |
| Кому сколько начислено | `partner_accruals` | **строим** |
| Что мы отдали | `partner_payouts` | **строим** |

Реестр партнёров (`partners`), реф-ссылка `/p/{ref_code}`, атрибуция тенанта,
уведомления через `platform_notify` и экраны владельца `/partners`, `/partners/{id}`
работают с Куска C — их расширяем, а не переписываем.

## 4. Два контура одной машины

У каждого контура ровно **один** источник денег. Это не упрощение ради красоты —
это то, как проект устроен на самом деле.

| Контур | Партнёр приводит | Клиент платит | Источник платежа | Врезка |
|---|---|---|---|---|
| **Платформенный** (наш) | тенанта | нам, за подписку | `service_invoices` | `mark_service_invoice_paid_by_payment` |
| **Тенантский** | лида тенанта | тенанту, за его продукт | `orders` | `_apply_order_paid` |

Различает их `partners.owner_tenant_id`: `null` — наша программа, не-null — программа
конкретного тенанта. Одна схема, одни расчёты, одни экраны; изоляцию делает RLS.

📌 Отдельного платежа «за внедрение» в коде сегодня нет: тенант платит подписку.
Поэтому «первый крупный» в нашем контуре сводится к **первой оплаченной абонплате**.
Если разовый вход появится, он придёт строкой `orders` — правило из §6 подхватит его
без правок кода.

## 5. Схема данных

Миграция `db/migrate_partner_money.sql`, аддитивная и идемпотентная, по правилу
expand-contract: **сначала `risuy_dev`, expand до кода, contract после деплоя кода.**

### 5.1 Расширение `partners`

```sql
alter table partners add column if not exists owner_tenant_id uuid references tenants(id);
alter table partners add column if not exists parent_id       uuid references partners(id);
alter table partners add column if not exists rate_percent    numeric(5,2) not null default 20;
alter table partners add column if not exists joined_at       timestamptz not null default now();
alter table partners add column if not exists login_actor     text;   -- ссылка на admin_users.username
alter table partners add column if not exists email           text;
alter table partners add column if not exists tax_status      text;   -- самозанятый | ип | физлицо | null
```

`owner_tenant_id is null` — наша программа (все существующие строки такие, бэкфилл не
нужен). `parent_id` — наставник; фиксируется при регистрации и **не перепривязывается**:
смена наставника задним числом переписала бы историю начислений.

⚠️ `default 20` в колонке — не второй источник истины, а только значение для строк,
заведённых до кода. Ставку новому партнёру проставляет код из `PARTNER_RATE_PERCENT`;
двойной источник (как `plans` против `config.SERVICE_PLANS`) в этом проекте уже стоил
разбирательства — повторять не будем.

### 5.2 `partner_accruals` — начисления

```sql
create table if not exists partner_accruals (
    id            uuid primary key default gen_random_uuid(),
    partner_id    uuid not null references partners(id),
    owner_tenant_id uuid references tenants(id),        -- копия контура: для RLS и отчётов
    source_kind   text not null,                        -- service_invoice | order
    source_id     uuid not null,                        -- id строки-источника
    client_kind   text not null,                        -- tenant | lead
    client_id     uuid not null,                        -- кто заплатил
    level         smallint not null,                    -- 0 продавец, 1 наставник
    rate_percent  numeric(5,2) not null,                -- КОПИЯ ставки на момент начисления
    amount_rub    numeric(12,2) not null,               -- отрицательная при сторно
    reason        text not null,                        -- sale | mentor | refund
    created_at    timestamptz not null default now(),
    constraint partner_accruals_level_chk  check (level in (0,1)),
    constraint partner_accruals_reason_chk check (reason in ('sale','mentor','refund')),
    constraint partner_accruals_kind_chk   check (source_kind in ('service_invoice','order'))
);
```

Два индекса несут смысл, а не скорость:

```sql
-- Повторный вебхук не начислит дважды.
create unique index if not exists partner_accruals_source_uq
    on partner_accruals (source_kind, source_id, partner_id, level)
    where reason <> 'refund';

-- 🔴 «Только первый платёж» — правило в БАЗЕ, а не в коде.
create unique index if not exists partner_accruals_first_sale_uq
    on partner_accruals (client_kind, client_id, level)
    where reason in ('sale','mentor');
```

Второй индекс физически запрещает второе продажное начисление по одному клиенту.
Гонка двух вебхуков, ручная правка, повторный прогон бэкфилла — не пробьют. Проверка
«а не начисляли ли мы уже» в коде была бы правдой ровно до первой параллельной оплаты.

### 5.3 `partner_payouts` — выплаты

```sql
create table if not exists partner_payouts (
    id           uuid primary key default gen_random_uuid(),
    partner_id   uuid not null references partners(id),
    owner_tenant_id uuid references tenants(id),
    amount_rub   numeric(12,2) not null check (amount_rub > 0),
    paid_at      timestamptz not null default now(),
    method       text,                                  -- карта | СБП | счёт ИП — свободный текст
    note         text,
    created_by   text not null,
    created_at   timestamptz not null default now()
);
```

**Колонки «баланс» нет.** К выплате = сумма начислений − сумма выплат, считается
запросом. Сохранённое вычисляемое значение расходится с фактом при первой же правке
задним числом.

### 5.4 `partner_invites` — одноразовые приглашения

```sql
create table if not exists partner_invites (
    token_hash  text primary key,                       -- sha256 от токена, не сам токен
    partner_id  uuid not null references partners(id),
    expires_at  timestamptz not null,
    used_at     timestamptz,
    created_by  text not null,
    created_at  timestamptz not null default now()
);
```

Образец — `password_reset_tokens` (сессия 3): в базе лежит хеш, не токен; ссылка живёт
72 часа; повторное использование отбивается `used_at`.

### 5.5 RLS

`partners` исторически платформенная таблица без RLS. С появлением тенантского контура
она обязана стать изолированной, иначе тенант увидит наших партнёров и наши ставки.

Contract-файл `db/migrate_partner_money_rls.sql` (после деплоя кода) включает RLS на
всех четырёх таблицах по канону проекта — обе ветки через `nullif`, как чинили
`tenant_agents` 03.08:

```sql
using (
    owner_tenant_id is not distinct from nullif(current_setting('app.tenant_id', true), '')::uuid
)
```

Платформенные строки (`owner_tenant_id is null`) видны только при пустом GUC, то есть
платформенному владельцу (`Session.is_platform`). Гранты `panel_rw` — select/insert/update,
delete не даём: начисления и выплаты не удаляются, а сторнируются.

## 6. Как начисляется

Обе врезки — **внутри существующей транзакции**, рядом с отметкой «оплачено», и обе
best-effort **не** являются: если начисление упало, платёж не считается принятым.
Это не уведомление, это деньги.

```
mark_service_invoice_paid_by_payment(payment_id, tenant_id=…)
  └─ статус → paid                       (уже есть, идемпотентно)
  └─ accrue_for_payment(c, kind='service_invoice', source_id=invoice.id,
                        client_kind='tenant', client_id=tenant_id, amount=invoice.amount)

_apply_order_paid(c, row, payment_id)
  └─ статус → paid, лид → converted      (уже есть, идемпотентно)
  └─ accrue_for_payment(c, kind='order', source_id=order.id,
                        client_kind='lead', client_id=order.lead_id, amount=order.amount)
```

`accrue_for_payment` — единственное место, где рождаются деньги партнёра:

1. Ищет партнёра клиента: `tenants.partner_id` для тенанта, `leads.partner_id` для лида.
   Нет партнёра — выходим молча, это обычный случай.
2. Партнёр `status='disabled'` — не начисляем.
3. Пишет строку продавца: `level=0`, `reason='sale'`, ставка — **копия
   `partners.rate_percent`** на этот момент.
4. Если у партнёра есть `parent_id`, контур **платформенный** и с `joined_at` продавца
   прошло меньше `MENTOR_BONUS_MONTHS` — пишет строку наставника: `level=1`,
   `reason='mentor'`, ставка `MENTOR_RATE_PERCENT`.
5. Конфликт по любому из уникальных индексов → `on conflict do nothing`. Повтор — не
   ошибка, а норма: вебхуки приходят по два раза.

Пополнения баланса токенов (`mark_topup_succeeded`) **не трогаем вовсе** — решение
владельца. Это единственный платёж, который не порождает начислений.

### 6.1 Сторно при возврате

Возврат в ЮKassa инициирует человек. При переводе заказа/счёта в `refunded` пишем
отрицательные строки `reason='refund'` по **всем** уровням разом. Иначе на возврате
партнёрская сеть зарабатывает, а мы платим дважды. Индекс первого платежа сторно не
блокирует (`where reason in ('sale','mentor')`), и это намеренно: после возврата
клиент может оплатить снова, и начисление должно пройти.

От двойного сторно защищает не индекс, а сам переход статуса: строки пишутся только в
той же транзакции, где источник **меняет** статус на `refunded`, а повторный вызов
видит `refunded` и выходит — тем же приёмом, что `_apply_order_paid` защищается от
повторного вебхука. Отдельного уникального индекса на сторно нет намеренно: возврат
может быть частичным и не один.

## 7. Чистые расчёты

Файл `admin-panel/partner_money.py` — функции без базы, потому что это чужие деньги:
ошибка здесь не падает, а тихо занижает выплату, пока партнёр не пересчитает вручную
и не придёт спорить.

- `accruals_for_payment(amount, seller, mentor, at) -> list[Accrual]` — кто сколько
  получает с одного платежа;
- `mentor_still_earns(seller_joined_at, at) -> bool` — срок наставнических, день в день
  ещё действует (граница в пользу партнёра);
- `partner_balance(accruals, payouts) -> (начислено, выплачено, к_выплате)`;
- `would_create_cycle(partner_id, parent_id, tree) -> bool` — A привёл B, B не может
  стать наставником A.

Константы — в `admin-panel/config.py`: `PARTNER_RATE_PERCENT = 20`,
`MENTOR_RATE_PERCENT = 5`, `MENTOR_BONUS_MONTHS = 12`, `PARTNER_MENTORS_TENANT_ENABLED = False`.

## 8. Кабинет партнёра

### 8.1 Вход

Партнёр — **не член команды тенанта**. `memberships` не трогаем: членство даёт доступ
к лидам, диалогам, знанию и расходам, а партнёру там делать нечего.

Владелец в карточке партнёра жмёт «Выдать доступ» → создаётся `partner_invites` с
одноразовым токеном → ссылка отдаётся партнёру (копированием или в Telegram через
`platform_notify`, если известен `tg_chat_id`). По ссылке партнёр вводит email и
пароль → создаётся `admin_users` с `role='partner'` → `partners.login_actor`
проставляется. Пароля мы не видим никогда; сброс — существующим механизмом
`/forgot-password` через почту `servis@pro-agent-ai.ru`.

### 8.2 🔴 Новый принципал закрывается белым списком

Это самое опасное место всей работы. В панели десятки маршрутов, и гейты в них писались
в мире, где принципала «партнёр» не существовало. Чёрный список («партнёру запрещено
вот это») пропустит всё, что добавят завтра.

Правило: `require_session` для `role='partner'` пропускает **только** префикс
`/partner/*`, всё остальное — 403, включая маршруты, которые появятся после этой
спеки. Партнёрская сессия не имеет `active_tenant_id` и не может его переключить.
Тест на это — не «партнёр не видит /companies», а «партнёр не видит НИ ОДИН маршрут
вне своего префикса», перебором по таблице маршрутов FastAPI.

### 8.3 Что видит партнёр

`/partner` — итоги: начислено · выплачено · к выплате, ниже приведённые клиенты
(название, дата, состояние) и начисленное по каждому. Своя реф-ссылка `/p/{ref_code}`
и число переходов. История выплат с методом и датой.

`/partner/team` — приведённые партнёры, их продажи **суммами** и начисленное с них,
плюс своя ссылка-приглашение. ⚠️ Чужих клиентов по именам наставник не видит: он
получает процент с оборота, а не доступ к чужой клиентской базе.

Пустой кабинет показывает онбординг («вот ваша ссылка, вот как это работает»), а не
пустую таблицу.

### 8.4 Что видит владелец

Карточка партнёра `/partners/{id}` дорастает разделами: начисления, выплаты, кнопка
«Отметить выплату», кнопка «Выдать доступ», поле ставки и выбор наставника. Список
`/partners` получает колонки «начислено» и «к выплате».

🔴 Суммы считаем **отдельными группировками и сшиваем в Python по словарю**, а не
коррелированными подзапросами в `select`. В x10 такой подзапрос молча вернул нули при
верных данных в базе — партнёр увидел бы «начислено 0» при оплаченной сделке.

## 9. 🔴 Экономика: цифра, на которую партнёр не поедет

Считано до постройки, а не после первой продажи. Тарифы — `config.SERVICE_PLANS`.

| | Эконом 3 750 ₽ | Стартовый 7 500 ₽ |
|---|---|---|
| Партнёру 20% | −750 | −1 500 |
| Наставнику 5% | −187 | −375 |
| Эквайринг ЮKassa ~3% | −112 | −225 |
| **Остаётся нам** | **≈2 700 (72%)** | **≈5 400 (72%)** |

Схема считается верно, и доля наша совпадает с ProAgent AI. Но **750 ₽ разово за
приведённого клиента не окупают партнёру даже разговор.** В ProAgent AI та же механика
даёт ему 36–70 тысяч, потому что чек 180–350 тысяч; здесь чек 3 750 ₽ в период.

Три способа это исправить, решение за владельцем:

1. процент с абонплаты за 12 месяцев вместо первого платежа (Стартовый → 18 000 ₽
   партнёру за клиента) — меняется одна константа и снимается индекс первого платежа;
2. ставка на первый платёж 30–40% — меняется одна константа;
3. партнёров нацеливают на «Индивидуальный» с договорной ценой, где 20% — уже деньги.

Строим как решено. Но цифру стоит вернуть на пересмотр **до** набора партнёров: менять
условия после того, как люди начали продавать, дороже во всех смыслах.

## 10. 🔴 Красная линия: за что платить нельзя

Вознаграждение за **привлечение участников**, не связанное с продажей товара или
услуги, — признак финансовой пирамиды (ст. 172.2 УК РФ). Пока доля идёт от реального
платежа клиента, это обычная агентская схема с субагентами.

Три правила зашиты в код, а не в договорённости:

1. Взносов за вступление нет — вход бесплатный всегда.
2. Начисление возможно ТОЛЬКО из строки `service_invoices`/`orders` со статусом `paid`.
   Никаких «бонусов за регистрацию» и «за активность».
3. Глубина ограничена константой `level in (0,1)` на уровне `check`-ограничения БД.

### 10.1 Наставников тенантам не даём

Для нашего контура схема А безопасна: мы платим со своих продаж и отвечаем за себя.
Но многоуровневая механика, выданная **третьим лицам**, — это инструмент, который в
чужих руках превращается в то, за что отвечать будет площадка, то есть мы.

Решение: `PARTNER_MENTORS_TENANT_ENABLED = False`. В тенантском контуре глубина 0 —
только прямые партнёры. Шаг 4 в §6 проверяет контур явно.

⚠️ Слова «структура», «уровни», «сетевой маркетинг» в интерфейсе не употребляем. Есть
«партнёр» и «наставник». Механика внутренняя: партнёр видит её в кабинете, клиент —
никогда.

## 11. Тесты вперёд кода

Смоуки по канону проекта (`scripts/partner_money_smoke.py`, зелёный на `risuy_dev`):

- 20% считаются от суммы платежа; ставка берётся **из начисления**, правка
  `partners.rate_percent` не трогает прошлое;
- второй платёж того же клиента начислений НЕ порождает (индекс первого платежа);
- пополнение баланса токенов не порождает начислений вовсе;
- наставник получает 5% **сверх**, продавец не теряет ничего;
- наставник наставника не получает ничего;
- после 12 месяцев наставнические прекращаются, день в день ещё идут;
- в тенантском контуре наставнических нет вообще;
- повторный вебхук по тому же `payment_id` не начисляет дважды (гонка: 20 параллельных
  вызовов → ровно одна строка, как проверяли слот демо-чата);
- возврат уменьшает начисленное отрицательной строкой по обоим уровням;
- «к выплате» = начислено − выплачено при нескольких выплатах;
- цикл в дереве наставников отбивается;
- RLS: тенант не видит ни партнёров платформы, ни чужих начислений; пустой GUC не даёт
  22P02;
- **гейт принципала:** перебор всех маршрутов FastAPI — партнёрская сессия получает 403
  везде, кроме `/partner/*`.

## 12. Порядок постройки

1. Константы + `partner_money.py` + смоук расчётов (без базы).
2. Миграция expand на `risuy_dev` → бэкфилл не нужен (все партнёры платформенные).
3. `accrue_for_payment` + врезка в обе точки + смоук идемпотентности.
4. Кабинет партнёра: приглашение, вход, белый список маршрутов, экраны.
5. Экраны владельца: начисления, выплаты, выдача доступа, ставка и наставник.
6. Contract-миграция RLS **после** деплоя кода.
7. Живой прогон на проде: партнёр, клиент, платёж, начисление, выплата — со снимком до
   и уборкой после.
8. Тенантский контур — отдельным этапом на этой же схеме.

## 13. Чего не делаем

- **Автовыплаты.** PayPal, Stripe и Wise в РФ не работают; перевод делает человек, в
  системе — отметка.
- **Трекинг кликов как основание выплаты.** Переходы по `/p/{code}` считаем для
  отчёта, деньги — только от платежей.
- **Готовый движок.** RefRef, Refferq, Raider, Dub проверены в ProAgent AI: все считают
  конверсией платёж в Stripe, а Dub self-host требует четырёх зарубежных SaaS —
  несовместимо со 152-ФЗ. Схему данных берём как ориентир, код пишем свой.
- **Акты и налоговые документы** — до ответа по §14.2.

## 14. Открыто, за владельцем

1. **Цифра комиссии** (§9). Строим 20% с первого платежа, но 750 ₽ партнёра не
   мотивируют. Нужен пересмотр до набора партнёров.
2. **Самозанятые или ИП.** От этого зависит, нужны ли акты в кабинете и кто платит
   налог с наставнических. Пока `tax_status` — свободное поле.
3. **Процент от суммы до налога или после.**
4. **Тенантский контур — когда включаем.** Схема заложена сразу, экраны и оферта для
   партнёров тенанта — отдельная работа: у тенанта свои договоры, свои деньги и свой
   152-ФЗ.
5. **Атрибуция задним числом.** Тенанта, заведённого владельцем вручную, сейчас
   привязать к партнёру нечем. Предлагаю действие в карточке партнёра — но это правка
   истории, и она должна попадать в аудит.
